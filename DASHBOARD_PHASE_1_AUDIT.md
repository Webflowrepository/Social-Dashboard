# Dashboard Phase 1 Audit

## Current Structure

The dashboard is a single Astro page at `src/pages/dashboard/index.astro` with one client script at `public/dashboard/app.js`.

Current sections:

- Header/navigation
- Website focus panel
- Newsletter focus panel
- Summary cards
- Global period/channel filters
- Registro table
- Channel comparison cards
- Source/setup queue

The dashboard currently behaves more like a content registry plus source-status panel than a full analytics product.

## Current Data Sources

Data is generated by `sync-socials.mjs` into:

- `public/dashboard/social-data.json`
- `public/dashboard/social-snapshots.json`

Working integrations:

- YouTube OAuth/Data API
- Beehiiv API
- Cloudflare zone analytics for website paths
- Public LinkedIn profile metadata
- Public Instagram profile metadata
- Manual CSV imports for LinkedIn/Instagram in `data/imports/`

Removed from current product surface:

- Spotify

## Current Analytical Problems

1. The dashboard is not organized around business questions.
   It starts with Website/Newsletter focus panels and then a registry, but does not clearly answer "what improved", "what declined", or "what should we replicate".

2. Channel analysis is uneven.
   Newsletter and Website have dedicated top panels. Instagram, LinkedIn, and YouTube are mostly pushed into channel cards and the registry.

3. One arbitrary score is doing too much work.
   Score is useful for sorting but not enough for analysis. Users need top content by concrete metrics such as likes, reach, clicks, opens, views.

4. Period comparison is missing.
   There is filtering by month/week/all, but no explicit previous-period comparison, absolute delta, or trend interpretation.

5. Metrics are not separated by analytical meaning.
   Audience metrics, publishing activity, engagement, traffic, and source setup status are mixed.

6. Learnings are not persisted.
   Current "Lectura" text is generated per row, but there is no institutional memory model with fact/observation/hypothesis/recommendation/status.

7. Low-data confidence is not represented.
   The dashboard can show rankings even when sample size is tiny, but it does not label evidence as strong, weak, or insufficient.

8. Filters are too limited for the proposed future.
   Current filters are period and channel only. There is no topic, format, campaign, or content type filtering.

9. Website is currently path-demand, not full website analytics.
   Cloudflare path views are useful, but they should not be presented as equivalent to GA4-style users/sessions/acquisition.

10. Source/setup status takes too much product space.
    It is operationally useful, but should move lower or into a settings/data-health area.

## Duplicated / Irrelevant / Misleading Items

- `missingFor()` in `public/dashboard/app.js` contains duplicate `youtube` keys; only the last value is used.
- `profile_proxy` rows are useful for data-health, but misleading inside performance rankings if mixed with real content.
- The summary card "Top canal" can select a channel based on a proxy score unless filtered carefully.
- Website path views and newsletter engagement are currently displayed close together, but they answer different questions and should stay analytically separate.
- The registry is useful for deep analysis, but it appears too early for quick-check usage.

## Components To Preserve

- Sync pipeline in `sync-socials.mjs`
- `social-data.json` and `social-snapshots.json`
- Beehiiv integration
- Cloudflare website path integration
- YouTube OAuth/Data API integration
- CSV import path for LinkedIn/Instagram
- Registry table foundation
- Period filtering primitives
- Channel/status metadata

## Components To Remove Or Reorganize

- Move "Que falta conectar" out of main analytical flow into Data Health.
- Replace generic summary cards with question-based overview cards.
- Split channel cards into dedicated channel sections/pages.
- Replace single "score-first" ranking with metric-specific rankings.
- Add explicit previous-period comparison and confidence labels.
- Move proxy/profile rows out of content-performance views.

## Data Model Assessment

Current model is JSON-based and can support a first refactor without database changes:

- `channels` maps to channel metadata/current totals.
- `contentItems` maps to content-level records.
- `social-snapshots` can support coarse historical trend.
- `sourceStatus` maps to data health.

Missing conceptual entities for the target system:

- `daily_metrics`
- `content_categories`
- `campaigns`
- `learnings`
- `analysis_periods`

Recommendation: do not add a database yet. First normalize the frontend around derived views from `contentItems`, `channels`, and `social-snapshots`. Add optional metadata fields (`topic`, `format`, `campaign`, `contentType`) to CSV/API items before introducing a schema.

## Phase 2 Direction

Recommended new architecture:

1. Overview
   Quick answer: what happened, what changed, what won, what needs attention.

2. Channel Sections
   Instagram, LinkedIn, YouTube, Newsletter, Website each get their own analytical block.

3. Content Performance
   Ranked content by concrete metrics, not only score.

4. Content Intelligence
   Topic/format/campaign analysis when metadata exists.

5. Learnings
   Fact, observation, hypothesis, recommendation, status.

6. Data Health
   API/CSV/source status and missing credentials.
